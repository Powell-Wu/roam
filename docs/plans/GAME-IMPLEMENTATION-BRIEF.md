## 1. 目标与文档关系

做成适合散步途中短暂打开、两人用一部手机共同完成的轻量冒险游戏。玩家能够快速开始，理解当前任务和下一步奖励，完成后看到旅程推进，结束后留下共同回忆。

本文件保存当前架构、数据兼容、视觉与验收约束；当前待办统一见 [路线图](ROADMAP.md)。[原游戏优化方案](../archive/2026-10/GAME-QUALITY-PLAN.md) 已归档，保留问题评估、检查证据和 M0/M1 细项。原生 ES 模块长期 UI 路线已经由本文件的 Svelte 决策替代；小屏操作、草稿恢复、资源预算、旅程进度和分层反馈仍是维护要求。

已完成的迁移与修复先复核、直接保留。开始新任务前读取 git status、差异、当前报告和路线图，以实际代码确定基线，保持已有工作。

本次范围不包含账户、云同步、双机联机、GPS 强制验证、真实地图服务或完整虚拟城市。首轮继续静态托管、离线使用、本机保存；这些选择符合当前一部手机同行的使用方式。

## 2. 技术决策

| 项目 | 已定方案 | 理由 |
| --- | --- | --- |
| UI | Svelte 5 稳定版 | 用组件组织卡牌、进度、奖励和日志，支持局部更新与组件样式 |
| 类型 | 新 UI 与配置使用 TypeScript | 明确行程、节点、任务、奖励和交互阶段的数据约束 |
| 开发与构建 | Vite | 开发预览、模块处理、生产静态输出；实施时锁定实际稳定版本 |
| 路由 | 保留 hash 路由和当前页面地址 | GitHub Pages 下深链接可用，旧入口继续有效；首轮不增加路由库 |
| 样式 | CSS 变量 + 组件样式 + 少量全局基础样式 | 复用现有视觉，收敛四份卡牌 CSS 的覆盖；首轮不引入通用后台 UI 套件或 Tailwind |
| 动效 | CSS / Web Animations API；需要弹簧手感时使用 Svelte 原生 motion | 当前翻牌已有浏览器动画实现，先复用并统一生命周期 |
| 数据 | 保留 IndexedDB 原子事务和跨标签通知 | 保持既有记录、去重、防重复积分与失败恢复能力 |
| 离线与更新 | 保留自维护 Service Worker，适配 Vite 产物 | 维持显式应用更新与表单保护，避免同时更换缓存机制 |
| 托管 | GitHub Pages 与 /roam/ 路径 | 2026-10-15完成仓库与网址迁移，保留原PWA id及数据库/存储身份，兼容旧路径数据迁移 |
| 验证 | Node 内置业务测试 + fake-indexeddb；增加 svelte-check 和 Playwright 关键流程 | 复用业务断言，补上 UI、触摸与旧版升级的浏览器证据 |

SvelteKit、SSR 和服务器 API 暂无本轮需求。Phaser 仅在未来出现角色移动或实时小游戏时评估，不进入当前卡牌主流程。

版本政策：实施当日核验 Svelte 5、Vite、TypeScript 等稳定发布，写入 package.json 与 package-lock.json；使用 npm ci 重现环境，不安装预发布版本，不在文档里预填未经验证的版本组合。本机现有 Node.js 24 优先复用。

资料：[Svelte 官方概览](https://svelte.dev/docs/svelte/overview)、[Vite 静态部署 / GitHub Pages](https://vite.dev/guide/static-deploy.html#github-pages)、[Web Animations API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Animations_API)。查阅日期：2026-10-09。

## 3. 源码与构建迁移（已完成的过程与维护约束）

迁移前 dist 曾是受版本控制的源码；下列步骤已完成，原文件去向见 [迁移清单](../archive/2026-10/MIGRATION-INVENTORY.md)。当前源码在 src/public，dist 是已忽略的生成目录，_site仅保留旧对照产物。以下顺序用于历史追溯，不再重新执行：

1. 固定当前提交、未提交差异、内容版本和检查结果；用独立测试来源保存无隐私的旧格式行程 fixture。
2. 把页面入口和脚本迁入 src，静态插画、图标和 manifest 迁入 public；初期保留原 dist，Vite 暂输出到已忽略的 _site，用于对照验证。
3. 首轮直接复用现有 .mjs 业务、存储、手势判定和更新服务。业务测试改为 import 源码，不再依赖构建目录；类型适配允许保留 JS 过渡，不一轮重写所有规则。
4. 建立 Svelte 页面与组件，并接入同一数据服务。每次操作先事务提交，再更新展示；动画不修改积分和任务状态。
5. 新界面、旧存档、旧入口升级与离线验证通过后，dist 才转换为生成目录；移除旧受跟踪源码前，确认每个文件已进入 src/public、归档或明确停用清单。
6. 最终 src/public/config 是提交对象，dist 是 CI 构建产物并加入忽略。同步 README、一键发布与 GitHub Actions，保留 publish.cmd 的使用方式。

建议目录职责：

| 位置 | 内容 |
| --- | --- |
| src/App.svelte、src/main.ts | 启动、路由与生命周期 |
| src/pages/ | 首页、出发、任务、收藏、日志、结算、设置 |
| src/lib/components/ | TaskCard、JourneyProgress、RewardFeedback、Passport、JourneyTicket 等 |
| src/lib/domain/ | 卡池、计分、行程规则；首轮保留现有 .mjs，后续按实际改动转 TS |
| src/lib/services/ | IndexedDB、更新、草稿、跨标签同步 |
| src/lib/config/、src/styles/ | 品牌来源、视觉变量、字体、基础布局与可访问性 |
| public/ | 当前使用的 WebP、SVG、图标、manifest 和必要静态文件 |
| scripts/ | 构建、内容版本、检查与发布编排 |
| tests/ | 业务用例、旧格式 fixture、浏览器关键流程 |

### 已落实的构建、版本与发布约束

- Vite base 对应当前 /roam/ 部署子路径；图片、manifest、Service Worker 以部署基路径解析，不能硬编码为域名根目录 /。manifest id继续保留/citywalk/。
- scripts/release.mjs 和 scripts/check.mjs 已递归处理 dist 下最终 JS、CSS、图片和其他静态产物，涵盖 assets 子目录和指纹文件；排除 source map 与仅供开发的资料。
- 内容版本基于最终产物生成：先 Vite build，再递归编目并计算内容哈希，再写 release.json 与 sw.js。二者不参与自身版本哈希；同输入重建应得到同版本，避免版本导入打包导致哈希循环。
- 设置页从本版本缓存中的 release.json 读取版本；版本查询本身不触发整页刷新。必要时为旧更新入口生成兼容 release.mjs，验证后决定兼容窗口。
- 保留 sw.js 的 URL、scope、消息协议与缓存前缀兼容；全部文件下载校验成功才标记离线可用，失败删除未完成的新缓存。
- worker 只在玩家显式应用更新时跳过等待；其他标签不丢弃草稿。验证旧标签在新 worker 接管后能继续操作，不发生新旧模块混用；需要时保留上一版本缓存至安全清理。
- npm run build 与 npm run release 共用 Node 构建编排，完成 Vite 构建、版本及缓存生成；npm run check 只检查，不修改产物。
- scripts/publish.mjs 的提交范围增加 src、public、新配置和开发文档，保留私人笔记、.env 和生成产物排除；直接调用 Node 构建编排以兼容 Windows，不依赖跨 shell 拼接。
- GitHub Actions 在上传 dist 前执行类型、业务、构建、资源及关键浏览器检查。功能检查失败停止发布，一键脚本的失败恢复、取消和重试行为保持可用。

## 4. 数据与状态约束

品牌、UI 和构建迁移首轮保持原 version:1 数据、卡片 ID、节点安排和积分；试玩随后升级至v2，当前第二轮JSON格式为v3，支持v1/v2输入。IndexedDB结构版本仍为1，名称 citywalk-for-two、object store state、key current 不变；清站点数据不是迁移方案。

同时保留原 URL、manifest id/start_url/scope、localStorage/sessionStorage key 与 BroadcastChannel 兼容。更名只改变显示文案和图形，不新建一个空数据库。

状态分为两类：

- 已提交状态：行程、抽中的卡、seen、完成情况、花费、暂停时间、历史、偏好。由 IndexedDB 事务产生权威结果，保留 revision 与跨标签核对。
- 临时界面状态：当前页、拖动距离、翻牌阶段、弹层、筛选和未提交表单。组件和草稿服务管理，不因组件重建而静默丢失。

抽卡/换卡/完成期间有明确阶段和重入保护；保存失败恢复可操作状态，不展示成功。指针取消、页面隐藏、导航和组件销毁时清理监听、计时器及动画。

花费草稿以行程 + 节点 + 卡片 ID 隔离；收尾草稿以行程 ID 隔离。切换相机、锁屏、返回前台、刷新和应用更新后，只恢复仍属于当前记录的草稿；换卡后不把旧花费带入新卡。

新增试玩、分支或调整点值时另立 schema 升级：先验证旧输入，再在成功操作的同一事务中迁移；不要把 TypeScript 类型当运行时校验。第一批升级为v2，第二轮主题升级为v3；备份支持v1/v2，导出当前格式。新行程保存规则版本、节点和点值/阈值、主题内容快照，历史按对应规则解释，旧行程不随新点值重算。数据库结构版本与 JSON schema 版本分别管理。

回退应用必须支持已经写入的数据格式。当前已写入v3时，只能回退到兼容v3的构建；已核验基线为r-42f02b38fe62。原v1/v2应用不能读取新增主题格式，兼容回退证据见 [当前报告](../reports/IMPLEMENTATION-PROGRESS.md)。

## 6. 玩法升级范围

以下三批功能及第二轮主题已实现；外部验收仍待开展。后续维护以当前报告和路线图为准，不将本节再次作为待开发清单。

### 第一批：把一局已有冒险打磨完整

沿用 48 张卡、短途/半日/自由、预算和场景筛选。显示当前站、待办状态与下一档奖励；普通完成采用页内盖章和节点推进，中途达档采用简短页内提示；收尾解释 +4 分并留下名字和回忆，集中展示最高奖励与新章。

旧短途目标 13、阈值 8/11/13；半日目标 20、阈值 12/16/20。三类奖励、额外奖励与最高档领取保持当前解释。自由或不计分模式不能出现虚构的目标分数。

### 第二批：精品试玩与任务联动

新增 15–20 分钟试玩：三张精选零消费卡，覆盖观察、对话、合作；每张约 3–5 分钟。默认少设置、直接出发，目标是进入后 30 秒内抽到第一张卡；这是体验目标，需要试玩测量。

试玩默认不计分，以完成纪念票作为奖励；不改现有模式的计分。一个共同分支，例如“寻找街角线索 / 观察城市声音”，影响后续候选与收尾描述；选择即时保存，刷新不重抽。

从现有卡片挑选 12 张试做双人提示和任务联动。包括轮流带路、一个人描述另一个人寻找、分别作答再揭晓。每张明确行动、谁先开始和何时算完成，避免新增每张都必填的表单。

2026-10-13第二轮补充：出发可选观察城市或默契挑战，分别组合现有48卡，提供不同开场、收尾问题与纪念票；主题内容与卡池存为行程快照。短途、半日和自由模式可用，试玩保留自己的分支。首次抽卡与换卡都使用最近三局的软权重，预算、场景、禁用及本局去重不放宽。人工验收按用户要求暂缓，结束后提醒。

### 第三批：重玩与纪念积累

- 最近三局已完成卡降低抽取权重；本局严格去重，预算/场景/禁用仍是硬条件，池不足时放宽近期偏好。
- 收藏区分“喜欢”“不抽”“完成过”。首批纪念章少量且有可理解条件，例如第一次出发、三类同行、发现不同任务。
- 首版成就从当前及保留历史推导，删除记录会重算，界面说明统计口径；永久纪念收藏另作显式产品决策。
- 结算生成可保存的纪念票，带日期、旅程名、所选方向、完成任务和一句回忆。图片导出随后实现；照片附件再单独设计压缩、容量、删除和备份方式。
- 声音先做翻牌、盖章与达档三个短音效，提供开关并适配浏览器用户手势要求。

更新：先加载旧应用并存测试行程和草稿，再部署新产物，下载后显式应用更新，核对旧数据、草稿、资源和版本。另测双标签、缓存安装中断、首次联网后断网重开与离线完成。测试来源与用户实际存档隔离，不能清空用户来源的数据。

设备：320×700、390×844、844×390、1100×850 模拟布局；真实 iPhone Safari/主屏幕、Android Chrome/安装入口分别验收。没有设备的项目明确记为待实机验证，不能用鼠标或尺寸模拟写成已通过。

质量目标：保持预缓存静态文件总量 <1 MiB 的现有预算，递归按未压缩文件字节统计；先核对引用并归档停用 story 图，再增加资产。首屏下载量单独记录。LCP ≤2.5s、INP ≤200ms、CLS ≤0.1 为性能目标，记录设备、网络、缓存及版本；INP 需要交互测量，动画时长与 Lighthouse 总分不能代替。[Web Vitals 官方说明](https://web.dev/articles/vitals)

建议命令契约：npm run typecheck、npm test、npm run build、npm run check、npm run test:e2e；npm run release 兼容现有一键发布并完成构建。迁移第一阶段落实这些命令与 CI。

邀请五对用户试玩：记录首次抽卡耗时、求助/误操作、换卡原因、是否理解下一奖励、是否顺利收尾；至少三对再玩一局。首轮目标至少四对无需口头解释完成首次抽卡与完成操作。用于发现问题，不作为统计留存结论。
